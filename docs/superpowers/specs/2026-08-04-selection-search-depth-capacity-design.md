# 选片搜索深度与候选容量设计

## 问题

票据 01 当前允许主选候选时长达到目标时长 `T` 后立即完成，实际 `26shidu` 运行因此得到恰好 30 秒、没有剪辑余量的候选池。

同次运行浏览了 260 个素材摘要，却只对 10 个素材读取完整索引。现有代码只强制全部分页被列出，不限制完整索引检查数量、分类覆盖或同类比较深度。该结果能证明最小 Agent 闭环可运行，不能证明搜索充分。

## 目标

- 主选候选时长必须达到目标时长的 150%～200%；
- 完整索引检查量随素材总数和必要分类数增长；
- 每个必要分类具有足够同类素材用于比较；
- 每个最终候选只能来自已检查素材，并至少有三个同类比较对象；
- 通过批量 Tool 控制 LLM 往返次数；
- 完成规则由代码校验，不能只依赖 Prompt 自律；
- 保持 `cut_index.json` 只读。

## 非目标

本改动不实现票据 02 的以下能力：

- 查看或追加原视频帧；
- 更新、删除已有候选；
- `alternate`、`needs_review`；
- 替代关系；
- 候选池形成后的多轮修订；
- 视觉证据确认。

本改动也不实现票据 03 的恢复、续跑或重走。

“完整索引检查”仍指读取素材的结构化索引，不等同于观看视频、帧或音频。

## 候选容量

设 Brief 目标时长为 `T`：

```text
1.5T <= 主选候选时间并集 <= 2.0T
```

30 秒 Brief 对应 45～60 秒主选候选。

规则：

- 同一候选属于多个分类只计算一次；
- 同一素材内重叠区间按时间并集合并；
- `selection_candidate_add` 在加入后超过 `2.0T` 时拒绝；
- `selection_finish_request` 在主选时间并集低于 `1.5T` 或高于 `2.0T` 时拒绝；
- Prompt 不再要求达到 100% 后立即结束，而是要求规划 150%～200% 的候选池。

已有已完成任务不迁移、不重写。新规则只作用于新运行和显式重新校验。

## 动态完整索引检查下限

设：

```text
N = 项目素材总数
C = required=true 的分类数
K = min(N, max(30, ceil(N * 20%), C * 8))
```

完成前必须检查至少 `K` 个不同素材的完整索引。

示例：

```text
N=20, C=4   => K=20
N=100, C=4  => K=32
N=260, C=4  => K=52
N=500, C=4  => K=100
```

分类规则：

- 每个必要分类至少关联 `min(8, N)` 个已检查的不同素材；
- 每个最终候选所属的每个分类，必须存在至少 `min(3, N-1)` 个不同于候选素材的已检查素材；素材数不少于 4 时即固定要求三个；
- 一个素材可以关联多个分类，但全局 `K` 按不同 `asset_id` 去重；
- 只读取完整索引、但未声明比较分类的素材不计入分类覆盖；
- 最终候选素材必须属于完整索引检查集合。

必要分类最终没有合适候选时，仍需检查八个与该分类最接近的素材，并用 `missing_reason` 说明淘汰结论。只有 Brief 判断变化时，Agent 才能把分类改为非必要；不能为了绕过搜索下限降级分类。Validator 不静默降低必要分类下限。

## 搜索流程

推荐流程写入运行时 Prompt 和 Skill：

1. 浏览全部素材分页的精简摘要；
2. 根据 Brief 建立动态分类；
3. 从全量摘要形成跨分类 shortlist；
4. 分批读取 shortlist 的完整索引，并声明每个素材服务的比较分类和入围理由；
5. 达到动态下限后复查分类覆盖与同类比较深度；
6. 若候选判断仍在变化，以十个素材为一批继续检查；
7. 搜索充分后一次性规划 150%～200% 主选候选；
8. 添加候选并请求完成。

代码不实现固定阶段状态机。Validator 只检查可确定事实：检查数量、分类关联、候选来源、同类比较对象和时长范围。“判断是否仍在变化”保留给 LLM，事件记录用于人工审计。

## 状态模型

新增完整索引检查记录：

```json
{
  "asset_id": "asset_xxx",
  "category_ids": ["category-001"],
  "shortlist_reason": "摘要显示人物表情强，值得与同类开头素材比较"
}
```

`AssetProgress` 增加：

```text
inspections: list[AssetInspection]
```

约束：

- `asset_id` 唯一；重复检查时合并分类，并使用最新非空理由；
- `category_ids` 必须引用现有分类；
- `shortlist_reason` 必填；
- 记录只表示完整索引已返回给 Agent，不表示看过真实画面；
- 保留现有 `opened_asset_ids`，用于兼容现有状态和简单进度展示；
- 新状态 Schema 仍兼容缺少 `inspections` 的旧文件，默认空列表。

## Tool 设计

保留单素材 `asset_get`，扩展参数：

```json
{
  "asset_id": "asset_xxx",
  "category_ids": ["category-001"],
  "shortlist_reason": "为什么值得完整检查"
}
```

新增批量 Tool：

```text
asset_get_batch
```

参数：

```json
{
  "inspections": [
    {
      "asset_id": "asset_xxx",
      "category_ids": ["category-001"],
      "shortlist_reason": "人物高能开头候选"
    }
  ]
}
```

规则：

- 每批 1～10 个素材；
- 批内 `asset_id` 不得重复；
- 调用前必须已保存分类；
- 素材和分类引用全部合法后才返回数据；
- 任一条非法时整批拒绝，不写部分状态；
- 成功时返回每个素材的完整索引，并原子更新检查记录；
- 每个素材继续产生可审计的 `asset_opened` 事件；
- 批次产生一条包含数量和素材 ID 的 `asset_batch_opened` 事件。

批量 Tool 减少 52 个素材对应的 LLM Tool 往返次数。单素材 `asset_get` 用于补查，不提供绕过检查记录的旧签名。

## Validator

`SelectionValidator` 增加 `total_assets`，并提供：

```text
required_inspection_count(state) -> int
validate_inspection_batch(...)
validate_search_depth(state)
```

`validate_search_depth` 检查：

- 已检查不同素材数达到动态 `K`；
- 每个必要分类达到八个不同素材，或素材总数更少时达到 `N`；
- 每条检查记录的素材和分类存在；
- 理由非空；
- 最终候选素材已检查；
- 每个候选所属分类至少有 `min(3, N-1)` 个其他已检查素材。

`selection_candidate_add` 在搜索深度尚未达标时拒绝，避免票据 01 无更新、删除能力的情况下过早固化候选。

`selection_finish_request` 再次执行搜索深度和 150%～200% 容量检查。

## Prompt 与 Skill

删除或改写：

```text
建立最小主选候选池
达到 100% 后立即完成
不要添加锦上添花候选
```

新增明确要求：

- 摘要浏览只用于召回，不能直接代替完整索引比较；
- 先分类，再按动态下限建立 shortlist；
- 每个必要分类至少检查八个潜力素材；
- 使用 `asset_get_batch` 分批读取；
- 达到最低数量不代表必须停止，候选仍变化时继续检查；
- 每个候选理由必须指出同类比较依据；
- 主选候选规划到 150%～200%。

Runner 初始消息向 Agent提供 `N`，Tool 在分类保存后返回当前 `K`、每分类检查进度和剩余缺口，避免 LLM 手算。

## 事件

新增或扩展：

- `asset_opened`：加入 `category_ids` 和 `shortlist_reason`；
- `asset_batch_opened`：记录批次素材 ID、数量；
- `change_validated`：记录检查批次参数和 blockers；
- `completion_validated`：搜索深度不足时返回精确缺口；
- `selection_completed`：记录 `inspection_count`、要求的 `K` 和主选时间并集。

不保存完整 Tool 返回内容，避免 `events.jsonl` 重复写入大段素材索引。

## 自动测试

测试不依赖网络：

1. 动态公式覆盖小、中、大素材数和分类数；
2. 260 个素材、4 个必要分类要求 `K=52`；
3. 批量 Tool 限制 1～10、拒绝重复和无效引用；
4. 批量任一条非法时状态和事件不出现部分成功；
5. 重复检查合并分类和理由；
6. 每必要分类少于八个时完成被拒绝；
7. 全局检查数不足 `K` 时完成被拒绝；
8. 候选未检查时新增被拒绝；
9. 候选缺少 `min(3, N-1)` 个同类比较对象时新增被拒绝；
10. 30 秒目标在 44.9 秒时拒绝，45～60 秒通过，60.1 秒拒绝；
11. 同素材重叠区间继续按并集计算；
12. 脚本化假模型走完全部分页、分类、批量检查、候选和完成；
13. `cut_index.json` 运行前后哈希一致；
14. 旧状态缺少 `inspections` 时可读取，但不能在新规则下直接完成。

## 真实验收

从空任务运行 `26shidu` 与 30 秒 Brief：

- 260 个摘要全部浏览；
- 至少 52 个不同素材读取完整索引；
- 四个必要分类各有至少八个检查素材；
- 每个最终候选至少有三个同类比较对象；
- 主选时间并集为 45～60 秒；
- 候选体现人物、空镜、不同活动和景别；
- 事件能证明批量检查与分类覆盖；
- `cut_index.json` 哈希不变。

本验收不要求查看帧，不把完整索引检查描述成视觉精读。

## 完成标准

- 搜索深度不再由 LLM 任意决定；
- 搜索数量随素材总数和必要分类数增长；
- 260 个素材项目至少检查 52 个完整索引；
- 主选候选池具有 50%～100% 剪辑余量；
- 每个候选具有可审计的同类比较基础；
- 未实现票据 02、03 的能力；
- 素材索引始终只读。
