# Agent 还是工作流：通用开发与架构决策指南

## 文档定位

本文面向开发者和技术负责人，用于判断一个 AI 功能应该实现为模型函数、确定性工作流、有限路由还是完整 Agent。

核心原则是：

> Agent 不是工作流的高级形态。应该选择能够满足需求的最简单、最靠左的架构。

---

## 一、架构坐标系：工作流与 Agent 是什么

### 1. Agent 的关键是控制权

判断一个系统是不是 Agent，不看模型调用次数、工具数量或类名，而看：

> 谁决定下一步做什么。

工作流由程序显式控制：

```text
程序判断状态 → 选择分支 → 调用模型或工具
```

Agent 由模型在受控范围内动态决策：

```text
模型读取目标与观察
→ 选择工具和参数
→ Harness 执行
→ 结果反馈给模型
→ 模型继续、改计划或停止
```

模型参与某个节点，不代表整个系统就是 Agent。只有模型开始影响后续行动、工具选择或终止判断，系统才具有 Agent 性。

### 2. 架构是一条连续光谱

| 层级 | 控制方式 | 适合场景 |
|---|---|---|
| 模型函数 | 程序调用一次模型 | 抽取、分类、评分、摘要 |
| Prompt Chain | 程序控制固定模型步骤 | 提纲、生成、润色 |
| 确定性工作流 | 程序控制状态和分支 | 数据处理、审批、媒体管道 |
| LLM Router | 模型从有限动作中选择 | 搜索、询问、直接回答 |
| 受限 Agent | 模型控制有限闭环 | 排障、研究、方案修订 |
| 完整 Agent | 模型持续观察、行动和重新规划 | 开放式长任务 |
| Multi-Agent | 多个 Agent 分工协作 | 可独立拆分的大型任务 |

越靠右，适应性通常越强，但运行成本、不确定性、治理要求和评测难度也越高。Multi-Agent 并不天然优于单 Agent。

## 二、参考架构：完整 Agent 由什么组成

完整 Agent 可以定义为：

> 接受目标，在受控环境中持续执行“观察—判断—行动—验证”闭环，直到目标完成、预算耗尽或需要人工介入。

其最小结构是：

```text
Goal 与完成标准
        ↓
Agent Runtime / Policy
        ↓
选择并调用 Tool
        ↓
Observation
        ↓
更新 State
        ↓
Verifier
        ↓
完成 / 重新规划 / 人工介入
```

### 1. Goal：目标和完成标准

Agent 接收的应该是结果目标，而不只是操作命令。目标必须同时包含约束和可判断的完成标准，否则系统无法可靠停止。

### 2. Agent Runtime：行动循环

Runtime 负责维护循环、组装上下文、执行工具、保存状态、控制预算和处理终止：

```python
while budget_available:
    decision = model.decide(goal, state, observations, tools)
    result = execute(decision)
    state.record(decision, result)
    if verifier.is_complete(goal, state):
        break
```

### 3. Tool Layer：受控行动能力

工具应具备：

- 严格的输入输出契约。
- 清晰的能力和副作用描述。
- 参数校验、超时和错误分类。
- 幂等性或重复执行保护。
- 可供 Verifier 检查的结果。

Agent 应通过受控工具行动，而不是默认获得无限制的 Shell、数据库或文件系统权限。

### 4. State、Context 与 Memory

- **State**：当前任务的事实状态，例如步骤、结果、预算和失败。
- **Context**：本轮决策实际提供给模型的信息。
- **Memory**：跨步骤或跨任务保留的历史经验。

长期记忆不是 Agent 的必要条件；可靠的任务状态才是。

### 5. Verifier：独立完成判断

模型声称完成不等于任务完成。Verifier 应尽量独立检查：

- 输出是否存在。
- 是否符合 Schema。
- 是否满足业务约束。
- 是否通过测试或可执行验证。
- 是否产生意外副作用。

Agent 的完成声明只是候选结论，验证结果才是系统事实。

### 6. Guardrails：自治边界

自主性每增加一步，Harness 都应增加相应约束：

- 最大步骤数、运行时间和费用。
- 工具权限与参数边界。
- 写操作审批。
- 重复调用检测。
- 可重试和不可重试错误分类。
- 无法判断时升级人工。
- 完整行动日志和可追踪性。

## 三、采用判据：为什么以及什么时候需要 Agent

### 1. “路径无法穷举”不是数学上的无限

只要工具、状态和最大步数有限，理论上就能把所有行为写成一个足够大的状态机。

因此，更准确的判断不是：

> 路径能不能穷举？

而是：

> 能不能以合理成本、足够可靠地显式编码完整决策策略？

### 2. 有限工具不等于行动空间很小

具体行动取决于：

```text
工具名称 × 工具参数 × 当前状态 × 历史结果 × 用户目标
```

即使只有一个 `search(query)` 工具，`query`、搜索结果和后续判断也可能包含开放的自然语言语义。

Agent 没有创造无限能力。它只是用模型近似下面的控制函数：

```text
当前状态 + 用户目标 → 下一动作
```

工作流把这个函数显式写进代码；Agent 将大量语义条件隐式压缩在模型策略中。

### 3. 什么时候应继续写规则

以下条件成立时，即使分支很多，也应优先使用状态机、规则引擎或工作流：

- 状态能够结构化表达。
- 分支条件能够准确计算。
- 异常类型相对固定。
- 正确动作有稳定业务规则。
- 分支可以自动测试。
- 对可复现性要求高。
- 错误代价较高。

例如：

```python
if candidate_duration < target_duration:
    include_alternates()
```

这类规则清晰、可验证，没有必要交给 Agent。

### 4. 什么时候 Agent 开始有价值

Agent 更适合以下情况：

- 中间结果会改变后续策略，而不只是触发机械重试。
- 每次行动能够获得新的外部证据。
- 工具选择或参数需要理解开放语义。
- 同一状态在不同用户目标下需要不同权衡。
- 失败后需要改变方法，而不是重复相同步骤。
- 用户更容易描述目标，而不是指定完整过程。
- 长尾需求使规则冲突和维护成本持续上升。
- 最终结果可以被独立验证或可靠审批。

关键限制是：

> 如果每轮看到的仍是同一组信息，Agent Loop 通常只是更昂贵的 Prompt Chain。

### 5. 比较风险调整后的总成本

工作流成本包括：

```text
规则开发 + 分支测试 + 冲突维护 + 长尾特例 + 需求变化
```

Agent 成本包括：

```text
Harness 开发 + 模型调用 + 结果评测 + 不确定性治理
+ 失败恢复 + 人工审批
```

只有当 Agent 能提供工作流无法经济实现的价值，或者风险调整后的总成本更低时，才值得采用。

## 四、选型与落地：应该选择哪一级架构

### 1. 架构选型表

| 问题特征 | 推荐方案 |
|---|---|
| 输入输出稳定、一次判断即可 | 模型函数 |
| 步骤固定、条件明确 | 确定性工作流 |
| 需要语义理解，但动作集合很小 | LLM Router |
| 需要少量取证、修订和验证 | 受限 Agent |
| 需要持续取证、重新规划和动态终止 | 完整 Agent |
| 子任务确实能独立并行且需要不同上下文 | Multi-Agent |

### 2. 渐进式 Agent 化

推荐按以下顺序增加自主性：

```text
结构化模型函数
→ 条件工作流
→ 有限语义路由
→ 受限工具调用
→ Bounded Agent
→ 经评测后扩大自主范围
```

每一步都应回答：

- 新增的自主性解决了什么真实问题？
- 相比上一层，质量或效率是否有稳定提升？
- 新增风险是否有对应的约束和验证？

### 3. 保持确定性的部分

以下能力通常不应 Agent 化：

- 精确计算和格式转换。
- Schema 与业务约束校验。
- 文件、数据库和外部系统写入。
- 删除、发布、支付等高风险操作。
- 机械重试和已知错误恢复。

更稳健的通用架构是：

```text
确定性预处理
→ 模型函数或受限 Agent
→ 独立验证器
→ 确定性写入
```

### 4. 不要从 Multi-Agent 开始

优先从单 Agent 和最小工具集验证价值。只有任务可以真正独立拆分、并行收益明确、上下文需要隔离时，才考虑 Multi-Agent。

多个角色名称不等于多个 Agent 有必要；它往往只会增加通信、汇总和一致性成本。

## 五、架构评审清单

在批准 Agent 方案前，逐项回答：

### 价值

- 下一步是否真的依赖运行时未知结果？
- Agent 每走一步是否能获得新证据？
- 用户目标是否难以稳定转成固定参数？
- 移除 Agent Loop 后，产品价值是否明显下降？

### 替代方案

- 程序能否更可靠地计算下一步？
- 模型函数、Prompt Chain 或 LLM Router 是否已经足够？
- 增加规则的长期成本是否真的高于 Agent 治理成本？

### 完整性

- 是否定义了目标、约束和完成标准？
- 工具是否有严格 Schema 和副作用说明？
- 是否持久化任务状态和行动轨迹？
- 是否存在独立 Verifier？
- 失败后是机械重试还是有依据地重新规划？

### 安全与运行

- 是否限制步骤、时间、Token 和费用？
- 写操作是否幂等、可逆或需要审批？
- 是否能检测重复调用和无效循环？
- 是否能在无法判断时请求人工介入？
- 是否能解释失败发生在哪一层？

### 评测

- 是否有代表性任务集？
- 是否比较过工作流基线？
- 是否衡量成功率、成本、延迟和人工介入率？
- Agent 的提升是否稳定，而不是只展示成功案例？

如果这些问题没有明确答案，应先完善问题定义、工具、验证器或评测体系，而不是直接扩大 Agent 自主性。

---

## 最终原则

1. Agent 的本质是模型参与控制，而不是系统调用了大模型。
2. 能函数化就先函数化，能用工作流解决就不要引入开放循环。
3. “路径无法穷举”应理解为显式策略不再经济，而不是路径数学上无限。
4. Agent 循环只有在每一步能够获得新证据时才有价值。
5. 模型负责开放语义和动态策略，程序负责精确执行和硬约束。
6. 完成必须由 Verifier 判断，不能只依赖模型自报。
7. 自主性、约束、可观测性和评测能力必须同步增长。
8. 选择满足需求的最左侧架构，并通过数据证明向右移动的必要性。
